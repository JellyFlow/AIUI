# 启动性能

AIUI 的启动性能主要取决于：从打开智能体，到用户看到第一个有效画面之前，首个 Page 或 Widget 需要完成多少工作。

AIUI 运行时会在启动阶段读取并解析入口文件，合并全局与页面样式，解析模板并创建节点树，加载首屏使用的自定义组件，执行应用与入口脚本，再把初始 `data` 应用到模板。随后，运行时完成首轮数据绑定、布局和绘制，画面才会提交到屏幕。

因此，优化启动速度的重点不是笼统地减小整个项目，而是缩短首屏关键路径。

## 保持首屏结构精简

首屏模板越大，运行时在首次渲染前需要解析、绑定、布局和绘制的节点就越多。只把用户打开智能体后立即能看到或操作的内容放在入口页面中。

- 避免在首屏挂载当前不可见的大型列表、复杂面板或多层嵌套结构。
- 把非首屏流程拆到后续页面，在用户进入对应流程时再加载。
- 为列表设置合理的初始数量，不要在 `data` 中一次放入完整数据集。
- 减少仅用于包裹布局、但没有实际样式或交互作用的节点。

使用 CSS 隐藏内容并不会让它退出模板解析和节点创建过程。对于启动时不需要的完整功能区，优先从首屏结构中移除，而不是只设置为不可见。

### 将独立页面单元拆成不同 Page

如果首页、详情页和设置页分别承担独立任务，应把它们实现为不同的 Page。不要把所有页面的模板、状态和事件逻辑都放进一个 Page，再通过 `ink:if` 和页面状态切换整套界面。后一种方式会持续扩大入口模板和入口脚本，也会让各页面的生命周期、数据和交互逻辑耦合在一起。

例如，下面的结构把首页和详情页都放在同一个 Page 中，不适合随着功能继续扩展：

```html
<page>
  <view ink:if="{{ currentView === 'home' }}">
    <!-- 首页内容 -->
  </view>

  <view ink:elif="{{ currentView === 'detail' }}">
    <!-- 详情页内容 -->
  </view>
</page>
```

更合适的方式是在 `app.json` 中分别注册两个 Page：

```json
{
  "pages": [
    "pages/home/index",
    "pages/detail/index"
  ]
}
```

用户需要查看详情时，再从首页跳转到详情页：

```javascript
wx.navigateTo({
  url: '/pages/detail/index?id=42'
});
```

这样入口页面只承担首页任务，详情页的模板、状态和业务逻辑也能保持独立。需要用新页面替换当前页面时使用 `wx.redirectTo()`；返回已有页面时使用 `wx.navigateBack()`。

`ink:if` 仍然适合同一页面内的局部条件内容，例如加载态、空状态、错误提示、权限提示或可展开区域。判断标准是：如果这部分内容拥有独立任务、完整布局或独立导航语义，就优先拆成 Page；如果只是当前任务的一种局部状态，则保留在当前 Page 中。完整路由用法参见[路由 API](/AIUI/api/route)。

## 控制首屏自定义组件数量

运行时在解析入口模板时会加载其中引用的自定义组件，并执行组件脚本。组件自身的模板、样式、嵌套组件和初始化代码都会进入启动关键路径。

- 首屏只引用立即需要的自定义组件。
- 避免为了很小的静态片段引入层级很深的组件树。
- 检查嵌套组件是否重复引入相同资源或执行相同初始化。
- 将复杂但非必要的功能放到后续页面，而不是预先挂载在入口页面。

组件化仍然有助于维护代码，但组件边界本身不会自动带来按需加载。应根据首屏是否真正需要该组件来决定是否引用。

## 减少同步脚本和资源初始化

应用脚本、入口脚本以及首屏组件脚本都会在启动阶段执行。模块顶层的同步工作会直接延迟后续生命周期与首帧。

- 不要在模块顶层进行大数组转换、深层对象复制或重复 JSON 解析。
- 不要在启动时创建尚未使用的媒体、设备或其他重量级对象。
- 将非首屏所需的计算和能力初始化推迟到用户进入对应流程之后。
- 谨慎在入口模块中使用 `with { type: 'image' }` 或 `with { type: 'sound' }` 导入资源；运行时会在模块求值时解码图片或初始化声音对象。

`onLoad` 中也应尽快结束同步工作。网络请求可以在首屏先显示稳定的加载状态，返回后再更新页面：

```html
<script setup>
export default {
  data: {
    loading: true,
    items: [],
  },

  async onLoad() {
    const response = await fetch('https://api.example.com/items');
    const items = await response.json();

    this.setData({
      loading: false,
      items,
    });
  },
};
</script>
```

这个方式不会消除网络等待，但可以避免把远程数据作为首帧出现的前置条件。加载中、空状态和失败状态应保持尺寸稳定，减少数据返回后的明显跳动。

## 精简初始 `data` 和数据绑定

入口脚本执行后，运行时会读取初始 `data`，并将这些字段应用到模板绑定。大型对象、长列表和大量表达式会增加初次数据转换与绑定成本。

- 初始 `data` 只保留首屏渲染需要的字段。
- 不要把接口完整响应直接放入页面状态；先提取界面真正使用的数据。
- 避免在多个节点上重复读取同一组深层字段。
- 对一次请求产生的相关变化使用一次 `setData()`，避免连续触发多轮更新。

不要为了减少调用次数而把无关的大对象一起传给 `setData()`。合并更新的目标是减少重复渲染，同时保持每次更新的数据范围清晰、必要。

## 优化首屏样式和媒体

运行时会在首屏建树前解析全局样式与页面样式，并在布局过程中为节点计算样式。首屏图片等资源则可能在首轮更新后继续加载，并在完成后触发新的绘制。

- 删除未使用的全局样式，避免让每个页面都承担无关规则的解析成本。
- 控制复杂选择器和深层节点结构，尤其是会作用于大量首屏节点的规则。
- 为首屏图片提供明确尺寸，避免资源完成后重新改变整体布局。
- 压缩图片并选择接近实际显示尺寸的资源，避免解码远大于显示区域的图片。
- 不要让非必要的视频、动画或音频在启动时自动进入准备或播放流程。

## 测量首个有效画面

启动优化应在目标设备和真实 AIX 包上测量。开发机中的一次启动结果不能代表设备上的冷启动表现。

建议同时记录以下时间点：

1. 智能体开始打开。
2. `onLoad` 中必要的同步初始化结束。
3. 第一个画面提交。
4. 首个包含有效内容的画面出现。
5. 首屏主要数据加载并稳定显示。

用 `performance.mark()` 和 `performance.measure()` 记录业务初始化阶段；用录屏、宿主性能事件或设备日志确认真正显示到屏幕的时间。重复进行冷启动测试，并使用中位数或分位数比较改动前后结果。

```html
<script setup>
export default {
  async onLoad() {
    performance.mark('home-data-start');

    const response = await fetch('https://api.example.com/summary');
    const summary = await response.json();
    this.setData({ summary });

    performance.mark('home-data-end');
    performance.measure(
      'home-data-ready',
      'home-data-start',
      'home-data-end',
    );
  },
};
</script>
```

`performance.measure()` 只能说明 JavaScript 任务花了多久，不能单独证明画面已经显示。评估启动体验时，应把脚本测量与首帧、首个有效画面一起观察。

## 当前能力边界

当前运行时可以解析 `app.json` 中的 `subpackages` 和 `preloadRule` 字段，但启动与导航路径尚未依据这些字段执行分包加载或分包预下载。不要把配置字段本身当成已经生效的启动优化。

在运行时提供完整的分包调度能力之前，优先通过精简入口页面、减少首屏组件和同步初始化、控制初始数据及资源成本来改善启动体验。

继续阅读[性能数据](/AIUI/guide/performance-data)，了解需要建立的性能基线；如果问题主要发生在页面已经显示之后，请参考[运行时性能](/AIUI/guide/performance-runtime)。
